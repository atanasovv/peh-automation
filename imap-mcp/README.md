# SuperHosting Mail MCP

Go MCP сървър за една IMAP кутия в СуперХостинг. Версия 0.2.0 поддържа
Streamable HTTP през отдалечен контейнер и локално стартиране през stdio.

## Деплойване зад съществуващия Traefik

Compose файлът е съобразен с предоставената PEH конфигурация:

- външна мрежа `peh`;
- HTTPS входна точка `websecure`;
- сертификати чрез `letsencrypt` и Cloudflare DNS;
- middleware `secure-headers@file`;
- основен MCP адрес `https://<MAIL_MCP_DOMAIN>`, например `https://mcp.lexiplay.app`.

На сървъра използвай директорията с Dockerfile, compose.yml и Go изходните файлове.
Копирай `.env.example` като `.env` и попълни стойностите, или ги задай в Arcane.
Избери отделен поддомейн и насочи DNS записа към същия Traefik.
Генерирай отделен токен за MCP, например с `openssl rand -hex 32`.
Той трябва да има поне 32 символа.

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

Съществуващият Traefik и услугата трябва да работят на една машина и в една и съща
външна мрежа `peh`, създадена от същия Docker/Podman потребител. При rootless
Podman използвай неговия Compose доставчик. Ако Arcane използва готови образи,
предварително компилирай и публикувай образа в избрания регистър, задай пълното
му име в `MAIL_MCP_IMAGE` и използвай `docker compose up -d --no-build`.

Контейнерът слуша на вътрешен порт 8080. Достъпът отвън минава през Traefik,
който обслужва TLS. В контейнера приложението работи като непривилегирован
потребител с файлова система само за четене. `/healthz` служи за вътрешния
healthcheck. Traefik маршрутизира `/` и съвместимия адрес `/mcp`.

## Свързване на MCP клиент

Задай URL `https://<MAIL_MCP_DOMAIN>` (например `https://mcp.lexiplay.app`) и custom header
`Authorization: Bearer <MCP_AUTH_TOKEN>`. Токенът е единственият източник на
достъп за тази еднопотребителска инсталация. При този начин на удостоверяване
остави `bearer_token_env_var` празно.

Паролата на пощата се задава само на сървъра чрез `EMAIL_PASSWORD`.
Контейнерът получава тайните от средата си. Arcane, хост администраторът и
администраторът на контейнерите имат достъп до тях. Пази локалния `.env`
с ограничени файлови права, извън контрол на версиите.

## Настройка в Windows

В настройките за MCP добави локален сървър. Посочи пълния път до .exe файла
като команда. Добави следните променливи в средата на сървъра:

| Променлива | Стойност |
| --- | --- |
| `IMAP_SERVER` | Входящият сървър от настройките на кутията, без порт |
| `EMAIL_ADDRESS` | Пълният имейл адрес |
| `EMAIL_PASSWORD` | Паролата на кутията |
| `EMAIL_DRAFTS_FOLDER` | По избор. Точното IMAP име на папката за чернови, ако автоматичното откриване не успее |

Връзката използва TLS на порт 993. Паролата се подава чрез средата на процеса.
Ако я въведеш в MCP конфигурацията, тя се съхранява в тази локална конфигурация.
Пази я извън чата и проекта. При промяна на настройките отвори нов чат.


По подразбиране локалният изпълним файл използва stdio. За ръчно HTTP стартиране
са нужни `MCP_TRANSPORT=http`, `MCP_AUTH_TOKEN`, `MCP_PUBLIC_HOST` и
по избор `MCP_LISTEN_ADDR` (по подразбиране `:8080`). В Compose тези настройки
вече са зададени. Локалният HTTP listener е предназначен за достъп през HTTPS прокси.

## Използване

- „Намери последните 10 писма от този подател.“
- „Прочети първото писмо и предложи отговор.“
- „Запиши този отговор като чернова.“ Провери в Outlook, че виждаш черновата
  в папката на същия акаунт. Ако записът върне неясен резултат, провери папката
  преди да повториш заявката.

Четенето извлича текстовата част. Приложенията и писмата само с HTML не се
обработват в тази версия. Сървърът има три инструмента — `search_mail`,
`read_mail` и `save_reply_draft`. Записът добавя чернова в указаната папка.
Изпращането се извършва ръчно в Outlook.

За дневен обзор Codex може да комбинира резултатите от пощата и готовия MCP за
задачи. Например „Прегледай писмата от тази седмица, сравни ангажиментите с
отворените ми задачи и предложи какво да добавя или обновя.“ Задачите остават
в съществуващата система.

## GitHub Container Registry

Workflow файлът в корена на хранилището, `.github/workflows/publish-image.yml`,
първо изпълнява тестовете и проверката на Go кода, след което компилира образ
за Linux amd64 и arm64.

При push към `main` публикува `ghcr.io/atanasovv/peh-mail-mcp:latest` и
tag с commit SHA. При push на Git tag като `v0.2.0` публикува image tags
`0.2.0`, `0.2` и SHA. Може да се стартира ръчно от GitHub Actions.
При pull request проверява компилирането, като публикуването е изключено.
Удостоверяването към GHCR използва автоматичния `GITHUB_TOKEN`.

За деплойване с публикувания образ, от директорията `imap-mcp`:

```sh
docker compose pull
docker compose up -d --no-build
```

В Arcane задай `MAIL_MCP_IMAGE=ghcr.io/atanasovv/peh-mail-mcp:latest` или
конкретен публикуван version/SHA tag. Ако пакетът в GitHub е private,
настрой GHCR удостоверяването на сървъра с права за четене на пакета.
